# Відповіді до Lab 3

Ціни — us-east-1 on-demand з тексту лабораторної (730 год/міс), без податків. Мій Lab 2 працює в eu-north-1, де ціни трохи інші; точну суму показує Cost Explorer.

## Міграція

**1. Що тарифікується щогодини у Stage 0 і чим це замінено.**

| Stage 0 | Stage 2 |
|---|---|
| ALB | Зник: Lambda має власний HTTPS endpoint (function URL) |
| Public IPv4 (2 на ALB + 1 на task) | Зникли: мережеві інтерфейси Lambda приватні, ALB немає |
| Fargate task | Lambda — оплата за запит і GB-секунди, idle = $0 |
| RDS instance | Aurora Serverless v2, 0–1 ACU, пауза через 5 хв простою |
| RDS storage (20 GB) | Aurora storage за фактичний обсяг (~1 GB) |

У моєму Lab 2 додатково: 2 секрети Secrets Manager ($0.40 кожен). Stage 2 радить SSM Parameter Store, standard параметри якого безкоштовні.

**2. За що платимо в ALB і IPv4.** За досяжність, а не за обчислення: постійно ввімкнений балансувальник у двох AZ, health checks, TLS termination, маршрутизацію і публічні адреси, яких бракує в IPv4. Це ціна того, що сервіс завжди готовий прийняти з'єднання. Lambda function URL переносить цю постійну інфраструктуру на AWS і вбудовує її в ціну запиту.

**3. Хто платить за 15 с resume Aurora.** Платить користувач, який прийшов першим після тиші: це його час. Компанія за паузу не платить, навпаки, економить. Прийнятно для демо, staging і внутрішніх інструментів, де користувачі знають про холодний старт. Це баг, коли перший запит — платіж, логін клієнта чи webhook партнера з timeout < 15 с, або коли SLA вимагає стабільної latency.

**4. CORS.** Origin — це scheme + host + port. У Stage 0 сайт і `/api/*` йшли через одну CloudFront-адресу, тож браузер бачив один origin. У Stage 2 сторінка з `https://demo…` викликає `https://<id>.lambda-url…`, а це інший origin, тому з'являється preflight і `Access-Control-Allow-Origin`. Щоб повернути один origin, треба додати function URL як другий origin CloudFront із behavior `/api/*` (OAC для Lambda або secret header) і збирати frontend з відносним API URL. Мій Lab 2 так і працює: CloudFront → ALB на `/api/*`.

**5. Цикл URL і Makefile.** `make aws-deploy` спершу деплоїть backend (CORS `*` на першому запуску), потім frontend, зібраний із `ApiUrl`. Наступний backend deploy читає `AllowedOrigins` frontend stack і звужує CORS. Той самий цикл у Lab 3: Cognito client потребує callback/logout URL сайту, а сайт потребує ID клієнта й authority на етапі build. Розрив такий самий: `make deploy-auth` бере `FrontendUrl` з outputs `spry-lab`, а `make deploy-frontend` — outputs `spry-auth`. URL сайту не залежить від Cognito, тому порядок однозначний: сайт → auth → rebuild сайту.

**6. Чому немає NAT.** NAT gateway коштує ~$33/міс плюс трафік, тобто більше, ніж увесь Stage 2. Lambda в VPC без NAT бачить лише ресурси VPC. Коли знадобиться зовнішній API (LLM provider, Stripe, а також JWKS Cognito для перевірки токенів), виклики падатимуть з timeout. Рішення: NAT gateway, VPC endpoint (якщо сервіс AWS, наприклад Bedrock), винести виклик в окрему Lambda поза VPC або, для JWKS, передавати ключі в конфігурації (так зроблено в upstream-репозиторії). У моєму Lab 2 task має public IP, тому backend може завантажити JWKS напряму.

**7. us-east-1.** Для користувачів в Україні кожен API-запит дорожчий приблизно на 90 мс (≈120 мс до Virginia проти ≈30 мс до Frankfurt). Статика не страждає, бо її віддає CloudFront edge. Для компанії з клієнтами в ЄС персональні дані зберігаються в США. Це питання GDPR: потрібні правова підстава передачі (SCC / EU-US Data Privacy Framework), DPA, оновлена privacy policy, а частина клієнтів (державні, медичні, фінансові) може контрактно вимагати зберігання в ЄС.

**9. Uptime monitor на /health.** Так, мій `/health` робить `SELECT 1`. Крім того, його вже кожні 15 с опитує ALB з кожного свого вузла, а кожні 30 с — ECS health check контейнера. На RDS це нічого не коштує, бо інстанс і так увімкнений. На Aurora Serverless монітор раз на хвилину не дав би паузи ніколи: 730 год × 0.5–1 ACU ≈ $44–88/міс. Як виправити без втрати монітора: розділити liveness (`/health` без БД — процес живий) і readiness/deep check (`/health/db`), який монітор викликає рідко або тільки ALB. Або перевіряти БД, лише якщо пул уже має відкрите з'єднання.

**10. Коли повертатися до контейнерів + RDS.** Коли Aurora не спить більше ~257 год/міс при 0.5 ACU (~35% часу) чи ~129 год при 1 ACU, вигідніший RDS instance (а reserved — ще вигідніший). Коли трафік ≈ 42M запитів/міс (~16 req/s цілодобово), Lambda наздоганяє Fargate + ALB. У Cost Explorer, фільтр за тегом `PROJECT_NAME`, групування за Usage type: стежити за `Aurora:ServerlessV2Usage` (ACU-hours), `Lambda-GB-Second` і `Request`. Сигнал — коли ACU-години або витрати Lambda стабільно, кілька тижнів поспіль, перевищують фіксовану ціну відповідного provisioned ресурсу.

**11. Чому Free Tier — погана основа для рішення.** Він тимчасовий (12 місяців) і стосується лише акаунтів, створених до 15.07.2025. Нові акаунти отримують кредити на 6 місяців. Архітектура живе довше: через рік рахунок стрибне до повної ціни, а переписувати систему тоді дорожче. Free Tier також покриває одну micro-інстанцію на акаунт, а не staging + prod + кілька проєктів. Рішення треба порівнювати за list price і реальним профілем трафіку.

## Автентифікація

**12. ID token vs access token.** ID token — для клієнта: хто користувач (email, name, `aud` = client id, `token_use=id`). Ним frontend показує email у header. Access token — для resource server: що клієнту дозволено (scopes, `client_id`, `token_use=access`). До API йде access token. Мій backend відхиляє ID token, навіть валідно підписаний (`tests/test_auth.py`).

**13. Public client + PKCE.** Будь-хто може відкрити JavaScript сайту, тож секрет у браузері не є секретом. Тому клієнт публічний (`GenerateSecret: false`). Без секрету той, хто перехопив authorization code (через redirect, history, логи, шкідливе розширення чи custom URL scheme), міг би сам обміняти його на токени. PKCE: застосунок генерує випадковий `code_verifier` і надсилає Cognito лише його хеш (`code_challenge`). Обмін коду вимагає оригінальний verifier, який є тільки в цій вкладці. Тобто PKCE доводить, що код обмінює той самий екземпляр клієнта, що почав вхід. У confidential client це робить client secret. Різниця в тому, що verifier одноразовий і створюється для кожного входу, тож у коді немає чого красти.

**14. Ціна Cognito.** Essentials: перші 10 000 MAU безкоштовно, далі близько $0.015 за MAU. При 50 000 MAU: 40 000 × $0.015 ≈ $600/міс (Lite — близько $0.0055/MAU, ≈ $220, але без managed login v2). Власну автентифікацію варто розглядати, коли рахунок за MAU порівнюється з вартістю команди, яка підтримує безпечну auth (хешування, MFA, reset, rate limiting, аудит, інциденти), або коли потрібні можливості, яких Cognito не має. Зазвичай спершу розглядають інших провайдерів чи self-hosted Keycloak/Ory, а не свій код.

**15. Два користувачі з одним email.** Зламаються таблиці, де власник зберігається як `sub`: meetings, учасники, налаштування. Людина після входу через Google не бачить своїх зустрічей. Зв'язування: `AdminLinkProviderForUser` прив'язує Google-ідентичність до наявного native-користувача, і далі вхід через Google дає `sub` старого. Робити це варто з Pre sign-up Lambda trigger, лише після підтвердження: користувач входить паролем або вводить код з email. Автоматично за email небезпечно: email від зовнішнього провайдера не завжди підтверджений або належить тій самій людині. Нападник, що створив IdP-акаунт з чужим email, отримав би доступ до чужого акаунта (account takeover). Навіть з `email_verified` провайдер не гарантує, що адреса досі належить тій самій людині.

**16. Чому Google secret у Cognito, а app client без секрету.** Cognito — сервер AWS: секрет зберігається на сервері, і його ніхто з користувачів не бачить. Cognito виступає confidential client для Google. App client працює в браузері, де кожен може прочитати код і пам'ять, тому будь-який його «секрет» був би публічним. Тому його захищає PKCE, а не секрет.

**17. Consent screen Google і фішинг.** Користувач бачить назву застосунку, логотип, домен (для Cognito — `<prefix>.auth.us-east-1.amazoncognito.com`, якщо не підключено custom domain і не верифіковано бренд) і перелік даних: email, профіль. Саме тут користувач вирішує, кому довіряє. Фішинговий застосунок може назватися «Spry» і виглядати так само. Тому важливі верифікований бренд, власний домен замість чужого/generic, мінімальні scopes і навичка перевіряти, який домен запитує доступ.

## Stretch: захист API

**Чому перевірка в backend.** Frontend — код на машині нападника: перевірку «чи увійшов користувач» можна вимкнути в DevTools, а API викликати напряму `curl`. URL API видно в JavaScript. Якщо перевіряє лише frontend, нападник читає і створює зустрічі без входу, перебирає дані й навантажує БД. Межа довіри — сервер: він перевіряє підпис за JWKS, `exp`, `iss`, `client_id` і `token_use`, і лише тоді виконує запит.

**Чому не `AuthType: AWS_IAM` на function URL.** IAM вимагає SigV4-підпису AWS credentials. Браузер їх не має. Довелося б додати Cognito Identity Pool для обміну токена на тимчасові AWS-ключі, підписувати кожен запит у JS і давати кожному користувачу IAM-роль. Це складно, і IAM доводить лише «має AWS-ключі цього пулу», а не ідентичність користувача для застосунку. Для людей у браузері правильний механізм — OAuth/JWT. AWS_IAM підходить для service-to-service викликів. (У моєму Lab 2 API за ALB, а не function URL, тому там IAM auth взагалі недоступний.)

**JWT authorizer на API Gateway.** Знімає з коду завантаження й кешування JWKS, перевірку підпису, `exp`, `iss`, `aud`/`client_id` і scopes. Невалідні запити відхиляються до виклику Lambda, тож за них не платимо Lambda і не будимо Aurora. Додає HTTP API: ~$1.00 за мільйон запитів (сам authorizer безкоштовний), ще один ресурс у стеку і трохи latency. Перевірка `token_use` і бізнес-авторизація (чиї це зустрічі) все одно лишаються в коді.
